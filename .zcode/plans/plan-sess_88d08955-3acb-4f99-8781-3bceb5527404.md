# Plan: 把 Complement workflow 改成 Test workflow（Complement + SyTest + complement-crypto）

参照 **Dendrite** 的「单一 workflow 多并行 job + alls-green 门控」模式。SyTest 和 crypto 初期都 `continue-on-error`（信息性基线，不阻塞 PR），只有 Complement 是必须门控。

| 操作 | 文件 | 说明 |
|---|---|---|
| 重命名+重写 | `.github/workflows/complement.yml` → `.github/workflows/test.yml` | 三 job + 门控 |
| 新建 | `Containerfile.sytest` | sytest-katrix 镜像（`FROM matrixdotorg/sytest` + Go 1.26） |

## 1. `test.yml` 结构

触发同原 complement.yml（push master / PR / nightly `0 4 * * *` / workflow_dispatch）。

```
jobs:
  complement:          # 必须，沿用现有逻辑（去掉无用的 docker:dind service）
  complement-crypto:   # continue-on-error: true，跨客户端 jr,rj
  sytest:              # continue-on-error: true
  integration-done:    # needs 三个，re-actors/alls-green，!cancelled()
```

### Job `complement`（保留+清理）
- 删除 `services: docker: docker:dind`（步骤里 `docker build` 用的是 runner 自带 daemon，dind service 从未被引用，是死配置）
- 其余不变：build `Containerfile.complement` → checkout `matrix-org/complement` → `go test -tags="msc2836 msc2946 msc3030 msc3874 msc3890 msisns" ./tests/...` → summary 表格 + 上传 log
- 注：`msisns` 可能是笔误（非标准 Complement tag），保留现状除非报错

### Job `complement-crypto`（新，`continue-on-error: true`）
参照 complement-crypto 仓库 `tests.yaml` 的跨客户端模式，自己写 job（上游可复用 workflow 硬编码了 Synapse 镜像，无法注入 katrix 镜像）。

步骤：
1. checkout katrix；setup-go 1.26
2. setup Rust（`dtolnay/rust-toolchain@stable` + `Swatinem/rust-cache`）
3. setup node 24 + pnpm 9
4. `docker build -f Containerfile.complement -t ghcr.io/akagiyui/katrix:complement .`（复用 complement 镜像）
5. checkout `matrix-org/complement-crypto` → `./complement-crypto`
6. checkout `matrix-org/matrix-js-sdk` → `./matrix-js-sdk`，构建（pnpm install / build，参照 complement-crypto 的 `install-js-sdk.sh`）
7. checkout `matrix-org/matrix-rust-sdk` → `./matrix-rust-sdk`，`cargo build`，导出 `LIBRARY_PATH`/`LD_LIBRARY_PATH` 指向 target/debug
8. 构建 rpc binary：`cd complement-crypto && go build -o ./rpc ./cmd/rpc`
9. 跑测试：
   ```
   cd complement-crypto
   go test -p 3 -v -json -tags='jssdk,rust' -count=1 -timeout 15m ./tests ./tests/js ./tests/rust | gotestfmt
   ```
   env: `COMPLEMENT_BASE_IMAGE=ghcr.io/akagiyui/katrix:complement`, `COMPLEMENT_ENABLE_DIRTY_RUNS=1`, `COMPLEMENT_CRYPTO_TEST_CLIENT_MATRIX=jr,rj`, `COMPLEMENT_CRYPTO_RPC_BINARY=$(pwd)/rpc`, `COMPLEMENT_CRYPTO_MITMDUMP=mitm.dump`, `COMPLEMENT_SHARE_ENV_PREFIX=PASS_`, `TESTCONTAINERS_RYUK_DISABLED=true`, `DOCKER_BUILDKIT=1`
10. `if: always()` 上传 log artifact
11. **job 级 `continue-on-error: true`** —— 不阻塞

**风险点**：JS SDK 的构建/接线需对照 complement-crypto 当前的 `ENVIRONMENT.md`/`install-js-sdk.sh` 微调；matrix-rust-sdk 构建慢（~10min）。这是本计划里最不确定的一块，首次跑可能需要根据实际报错调一两次 SDK 路径/构建方式。

### Job `sytest`（新，`continue-on-error: true`）
关键架构：SyTest 的 per-homeserver 逻辑在 sytest 仓库的 `lib/SyTest/Homeserver/<Name>.pm` + `scripts/<name>_sytest.sh`，Docker 镜像本身很薄（base + Go + entrypoint）。我们不往 sytest 上游提交，而是在 CI 里 checkout sytest 后把 katrix 的 `Katrix.pm`/`katrix_sytest.sh` 拷进去，再 bind-mount。

步骤：
1. checkout katrix
2. checkout `matrix-org/sytest`（ref `develop`）→ `./sytest-src`
3. 拷贝：`sytest/Katrix.pm` → `sytest-src/lib/SyTest/Homeserver/Katrix.pm`；`sytest/katrix_sytest.sh` → `sytest-src/scripts/katrix_sytest.sh`；`chmod +x`
4. `docker build -f Containerfile.sytest -t sytest-katrix .`（`DOCKER_BUILDKIT=1`）
5. 运行：
   ```
   docker run --rm \
     -v $PWD/sytest-src:/sytest:ro \
     -v $PWD:/src \
     -v $PWD/sytest-logs:/logs \
     -e POSTGRES=1 -e SYTEST_DEFAULT_BRANCH=develop \
     sytest-katrix
   ```
   （`/sytest:ro` 同 Dendrite 的 run-sytest.sh 做法；`install-deps.pl` 在 base 镜像构建时已跑过，运行时幂等）
6. `if: always()`：解析 `/logs/results.tap` 写 summary 表格 + 上传 logs artifact
7. **job 级 `continue-on-error: true`**

### Job `integration-done`（门控）
```yaml
integration-done:
  needs: [complement, sytest, complement-crypto]
  if: ${{ !cancelled() }}
  runs-on: ubuntu-latest
  steps:
    - uses: re-actors/alls-green@release/v1
      with:
        jobs: ${{ toJSON(needs) }}
```
sytest/crypto 因 continue-on-error 结论恒为 success，故门控实际只拦 complement。

## 2. `Containerfile.sytest`（新建）

移植自 sytest 的 `dendrite.Dockerfile`：
```dockerfile
ARG SYTEST_IMAGE_TAG=bookworm
FROM matrixdotorg/sytest:${SYTEST_IMAGE_TAG}
ARG GO_VERSION=1.26.0
ARG TARGETARCH
RUN mkdir -p /goroot /gopath \
 && wget -q "https://dl.google.com/go/go${GO_VERSION}.linux-${TARGETARCH}.tar.gz" -O go.tar.gz \
 && tar xf go.tar.gz -C /goroot --strip-components=1 && rm go.tar.gz
ENV GOROOT=/goroot GOPATH=/gopath PATH="/goroot/bin:${PATH}"
ENV SYTEST_DEFAULT_BRANCH=develop
RUN mkdir -p /src
ENTRYPOINT [ "/bin/bash", "/bootstrap.sh", "katrix" ]
```
构建快（仅下载 Go tarball 叠在已发布的 base 上）。`TARGETARCH` 由 buildx 自动注入。

## 3. `sytest/Katrix.pm`（新建，移植自 Dendrite.pm）

katrix 的 CLI 契约与 Dendrite **不同**（无 `generate-config`/`generate-keys`；env/config-file 驱动），所以模块要适配：

- **`_get_config`**：不调用 `generate-config`，直接写一个 per-instance `katrix.yaml`：
  ```yaml
  server_name: <bind_host:secure_port>
  public_base_url: https://<bind_host:secure_port>
  listen:
    client: <bind_host:unsecure_port>     # http
    federation: <bind_host:secure_port>   # https (TLS)
  database:
    dsn: <pg_uri from POSTGRES_DB_1/2>
  signing_key_path: <hs_dir>/signing.key
  registration:
    enabled: true
  federation_enabled: true
  federation_tls:
    cert_path: <hs_dir>/server.crt
    key_path: <hs_dir>/server.key
  ```
- **`_generate_keyfiles`**：
  - signing key：`katrix genkey > <hs_dir>/signing.key`（`genkey` 打印 `ed25519 <ver> <seed>`，正是 katrix 签名密钥文件格式）
  - TLS cert：katrix `gencert` 必须要 CA，sytest 不挂 CA → 用 openssl 直接生成自签名 cert（等价于 Dendrite `generate-keys` 的自签名）：`openssl req -x509 -newkey rsa:2048 -nodes -keyout server.key -out server.crt -subj "/CN=<server_name>" -days 365 -addext "subjectAltName=DNS:<server_name>,DNS:localhost,IP:127.0.0.1"`
- **`_start_monolith`**：`katrix serve --config <hs_dir>/katrix.yaml`（katrix 的 `configPath` 识别 `-config`/`--config`）；端口监听在 yaml 里，无需 CLI flag。client = http（unsecure_port），federation = https（secure_port）。映射到 Dendrite::Monolith 的 `monolith`（secure）/`monolith_unsecure` 端口结构一致。
- 端口分配、`_start_process_and_await_connectable`、env 透传等沿用 Dendrite.pm。

## 5. 预期与风险（诚实评估）

- **SyTest**：katrix 早期，SyTest 用例预计 >90% 失败。首跑价值是建立基线 + 验证 `Katrix.pm`/bootstrap 管线能跑通。`Katrix.pm` 的 Perl 正确性是最大风险，可能需要几轮根据 sytest 实际报错调整（config 字段名、端口探测、TLS）。
- **complement-crypto**：JS/Rust SDK 构建接线最不确定，预计测试大面积失败，首跑主要验证镜像能被 complement-crypto 拉起。
- 两者 `continue-on-error`，不阻塞 PR；Complement 仍为唯一硬门控。
- 整个 test.yml 三 job 并行，crypto job 因构建两套 SDK 会是耗时最长的一条线（~20-30min）。

## 实施顺序
1. `git mv` complement.yml → test.yml，重写为三 job + 门控（complement job 先跑通）
2. 加 `Containerfile.sytest` + `sytest/*` 支持文件，开 sytest job
3. 加 complement-crypto job
4. 推上去观察首跑，按实际报错微调 `Katrix.pm` 和 crypto 的 SDK 接线
